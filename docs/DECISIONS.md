## 一、用途與前向 SSOT 宣告

- **用途**：記錄客戶裁示與正式決策，讓後人不必翻聊天就能查到「誰在何時決定了什麼、出處在哪、能不能撤回」。
- **前向 SSOT**：自 **2026-10-16** 起，新的客戶裁示與正式決策一律**追加於本檔第四節**。
- **交接本第 5 節自此凍結為歷史**：`docs/handover_2026_09_26_latest.md` 第 5 節〈待客戶裁示〉與各〈已裁示（日期）〉區塊（約 :3841-4184）保留原文、不再續寫；歷史裁示不複製進本檔，以第五節的索引指回原處。
- **登記不構成動工授權**（`CLAUDE.md` §-1，約 :1948）：一筆裁示被記在這裡，不代表它所涉及的工作可以開工；開工仍依 `CLAUDE.md` §-1 與 `PROJECT_RULES.md` 第 3、4 節。

## 二、provenance 標記規範

每筆條目必須標明出處性質，四種之一：

| 標記 | 意思 | 可不可以寫成「客戶裁示」 |
|---|---|---|
| **逐字** | repo 內或本機對話紀錄可核對的客戶原話，一字未改 | 可以 |
| **要點轉述** | 客戶在對話中裁示，經總管或協作助手轉達；repo 內無逐字原文 | 可以，但必須寫「要點轉述」與轉達人 |
| **總管裁決** | 總管依既有條文推導的判斷（例：`CLAUDE.md` §-1.5.1b 兩項裁決） | **不可以**；必須寫「總管裁決，可被客戶推翻」 |
| **agent 推論** | 執行組、稽核組或文件組的判讀 | **不可以**；不得列為裁示，只能寫在「理由／背景」欄當參考 |

- 同一筆裡混有客戶裁示與總管技術裁定時，分開寫（前例：交接本第 5 節 2026-10-14 第 60 點，約 :3941，「總管的技術裁定（不是客戶裁示）」）。
- 轉述的條目不得事後被改寫成逐字；拿到原文後另起一行補記，舊行保留。

## 三、條目欄位

| 欄位 | 寫什麼 |
|---|---|
| Decision ID | `DEC-YYYY-MM-DD-NN`（同日流水號，自 01 起）。只用於本檔第四節的新條目；歷史索引用第五節的出處 ID，不另起流水號 |
| 日期 | 客戶裁示的日期（不是寫入日期；兩者不同時都寫） |
| 決策內容摘要 | 一兩句；要點轉述者不得增刪語意 |
| 理由／背景 | 為什麼有這一筆；agent 推論只能放這裡並標明 |
| evidence／source | 可追溯的位置：PR、commit、檔案與行號、交接本節點 |
| 影響範圍 | 影響哪些檔、哪些頁、哪些規則 |
| 是否可逆 | 可逆／不可逆／未記載 |
| supersedes／superseded by | 取代了哪一筆、被哪一筆取代；被取代者不刪，加刪除線並註明 |
| provenance | 第二節四種之一 |
