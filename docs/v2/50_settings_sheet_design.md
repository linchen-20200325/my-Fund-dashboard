## 4. 每頁欄位

**共通的儲存格式**（`44` §4 開頭：時間欄存世界協調時間、日期欄不帶時間、不可空的欄取不到值就整列不寫）：

| `44` 型別 | 儲存格內的字面格式 | 例 |
|---|---|---|
| 字串 | 原字串 | `vol_index` |
| 日期 | `YYYY-MM-DD` | `2026-09-25` |
| 時間 | ISO 8601、世界協調時間、秒為單位、結尾 `Z` | `2026-09-26T03:14:15Z` |
| 浮點 | 十進位字面，小數點用半形句點，不加千分位 | `17.42` |
| 整數 | 十進位字面，不加千分位 | `42` |
| 布林 | `TRUE` 或 `FALSE` | `FALSE` |
| 空值 | **空儲存格**。不寫 `0`、不寫空白字元、不寫 `None`、`nan`、`null` | |

- 寫入一律用 `value_input_option="RAW"`：儲存格存的就是上表的字串，不讓試算表自動把日期、數字轉成它自己的型別（自動轉換會隨試算表的地區設定改變，讀回來的字串就對不上）。⚠️ 這一點**刻意與** `services/nav_history_gs.py::append_points` 用的 `USER_ENTERED` **不同**。
- 讀取一律取字串（`get_all_values`），由讀寫模組依上表嚴格解析。**解析不了的列不收**，並計數回報（第 8 節），不猜、不補。

## 5. 鍵的設計與「修正值不覆蓋原列」

### 5.1 `user_setting`：邏輯主鍵 `setting_key`，儲存端是事件列

- `44` 的主鍵是 `setting_key`（每個鍵只有一列）。若直接照這個形狀存，改設定就要**覆寫**那一列 —— 違反第 6 節的只追加規則，而且覆寫一半失敗會留下半新半舊的列。
- 所以儲存端改成事件列：`user_setting_log` 同一個鍵可以有很多列，**依列的先後**（試算表的列號）取最後一列。不用 `updated_at` 排序：同一秒內存兩次時 `updated_at` 相同，列號不會。
- 讀取端輸出的仍是 `44` 的形狀：每個鍵只有一列、四欄。

### 5.2 `market_indicator`：主鍵（`indicator_key`, `obs_date`, `release_date`）

- 這正是 `44` 的主鍵，`44` 自己就寫「同一期間被修正多次時各成一列，修正不覆蓋原列」，儲存端照做即可。
- ~~**寫入前去重**：先讀出分頁上已有的主鍵集合，只追加沒出現過的主鍵（比照 `services/nav_history_gs.py::append_points` 的「讀一次去重＋一次 `append_rows`」）。~~
  → **2026-09-26 稽核後改寫**（決策者：AI 總管；有意識的更正，不是漏刪）。舊表述只在寫入前去重，而第 6 節卻說「讀取端都去重」—— 兩句互相矛盾，第 6 節那句對 `market_indicator` 不成立。更根本的是：五個 app 是五個獨立行程（`49` §4.8），兩個行程同時「先讀主鍵、再追加」時，彼此看不到對方剛追加的列，**寫入前去重本來就擋不住重複**。**現行規則兩道都做：**
- **寫入前查主鍵（盡力而為）**：先讀出分頁上已有的主鍵集合，只追加沒出現過的主鍵（比照 `services/nav_history_gs.py::append_points` 的「讀一次去重＋一次 `append_rows`」）。它的用處只是減少重複列，**不是正確性的保證**。
- **讀取端依主鍵去重（正確性靠這一道）**：讀出全部列後，依主鍵（`indicator_key`, `obs_date`, `release_date`）分組：
  - ~~同一主鍵的列，除 `fetched_at` 以外的欄逐字相同 → 視為同一筆，取列號最小的一列；~~
  - ~~同一主鍵的列，`value_num`（或其他非 `fetched_at` 欄）不同 → **主鍵相同、數值不同**，見下一條。~~
  → **2026-09-26 複驗後更正**（決策者：AI 總管；有意識的更正，不是漏刪）：舊表述把 `is_revised` 也算進相等比較，但 `is_revised` 會在讀取端重算（見下方 `is_revised` 那一條），兩個行程寫下的同一筆可能只差在這一欄，舊規則會把它們誤判成「主鍵相同、數值不同」。**現行**：
  - 同一主鍵的列，**除 `fetched_at` 與 `is_revised` 以外**的欄逐字相同 → 視為同一筆，取列號最小的一列，`is_revised` 用重算後的值；
  - 同一主鍵的列，`value_num`（或其他排除上述兩欄後的欄）不同 → **主鍵相同、數值不同**，見下一條。
- **修正值**：來源對同一 `obs_date` 給出較晚的 `release_date` 與新的 `value_num` → 追加一列新列，`is_revised` 為 `TRUE`；舊列一個字都不動。`44` 的表判準「表上該期間有兩列且舊列的 `value_num` 未被改寫」由此成立。
- `is_revised` 的判定：同一（`indicator_key`, `obs_date`）已存在 `release_date` 較早的列 → `TRUE`；否則 `FALSE`。FRED 的公布日與版次屬 `49` T1，T1 實作前那三鍵不寫列（`49` §2.6）。⚠️ 同樣有多行程的 race：兩個行程同時寫同一 `obs_date` 的不同 `release_date` 時，兩列可能都寫成 `FALSE`。讀取端依同一條規則以列集合重算，與儲存值不符時以重算值為準，並在 SET 頁計數顯示「`is_revised` 與重算不符 N 列」，不靜默改寫試算表。
- **主鍵相同、數值不同（判定移到讀取端）**：這不是修正（修正會有新的 `release_date`），是兩次取數互相矛盾，沒有依據判斷哪一個對。
  - **讀取端**：該主鍵的**所有**列都不採用（不挑一個當真），在 SET 頁以 🟡 顯示「主鍵矛盾 N 組，未採用」，可展開看主鍵與各列的數值。
  - **寫入端**：寫入前查主鍵時若已看到同主鍵、不同數值 → 不追加，這一次取數的 `fetch_log` 記 `failed`，`message` 寫出主鍵與兩個數值。訊息文字是本系統產生的，不是來源原文，比照 `49` §6.1 配息頻率對照表規則 1 的先例（總管 2026-09-26 裁定）。
  - 寫入端沒看到（race）而讓矛盾的列落了地，由讀取端那一道擋下；那一次取數的 `fetch_log` 會是 `ok`，矛盾只會出現在 SET 頁的計數上 —— 這是 race 下唯一能誠實呈現的地方。

### 5.3 `fetch_log`：主鍵 `log_id`

- **`log_id` 組法**：取數開始時產生，`<started_at 的 ISO 字面>-<8 個十六進位隨機字元>`。只在同一次取數內傳遞，不重算。五個 app 是五個獨立行程（`49` §4.8），用時間加隨機字元避免兩個行程同一秒撞號。
- **一次取數寫兩筆**：開始時追加一列到 `fetch_log_open`；結束時（成功或失敗）追加一列到 `fetch_log`。
- **讀取端合併**：`fetch_log` 的列照原樣；`fetch_log_open` 裡有、`fetch_log` 裡沒有、且 `started_at` 已超過中斷判定時限的 `log_id` → 產生一列 `finished_at` 為空、`outcome` 為 `failed` 的列，`message` 為固定的系統文字「取數沒有結束紀錄」。時限與文字列入第 10 節。
- **同一 `log_id` 在 `fetch_log` 出現兩列**（寫入重試造成，見第 6 節）→ 讀取端取第一列，並在 SET 頁計數顯示「重複紀錄 N 筆」，不靜默吃掉。

## 7. 欄位標頭的鎖定與失敗訊息遮蔽的落點

### 7.1 標頭鎖定

- **第 1 列是標頭**，內容逐字等於第 4 節各表的欄位名與順序。讀寫模組把標頭寫成常數，**常數本身比照 `49` §3.3 第 2 步的欄位契約，以一條測試從 `44` 逐欄重抽比對**，漂了就紅（`44` 是真相源，常數是鏡像）。
- **每次打開分頁先讀第 1 列比對**。不一致 → 該分頁不讀也不寫，回報 ⛔「標頭與規格不符」並列出兩邊的差異。
- ⚠️ **刻意不自動修標頭**：`repositories/pool_repository.py`（`GoogleSheetsPoolStore` 內）與 `services/nav_history_gs.py` 在寫入路徑遇到標頭不符時會直接 `ws.update("A1", …)` 改寫標頭。本本不這樣做：分頁下面已經有資料時，改寫標頭等於把每一欄的語意換掉，而資料一格都沒動 —— 讀回來會是錯欄。
- **零列的分頁**（2026-09-26 回修第 3 輪新增；**有意識的更正，不是漏刪**；決策者：AI 總管）：分頁存在但完全零列（連標頭都沒有）時，讀取路徑視為「尚無資料」；寫入路徑**寫一次標頭（不重試）再照常追加**。本實作第一版把這種分頁當成「標頭不符」停下、不代寫標頭；~~總管第 2 輪另裁「剛建的分頁寫標頭失敗就刪掉該分頁」~~ —— 該裁示已撤銷：它違反第 6 節「不刪分頁」，而且標頭可能已送達、另一個寫入者可能已在後面追加，刪分頁會把那些列一起刪掉。**兩邊理由並陳**：不代寫標頭的理由（改寫標頭會把每一欄的語意換掉）只在分頁**已有列**時成立，那種情形照舊停下；零列時寫標頭不改變任何既有資料的語意，拒寫只會讓這張分頁永遠卡住。標頭寫入失敗（含 429）照第 8 節登記冷卻，不刪、不清。⚠️ **已知風險，未防護**：兩個使用者（或兩個行程）同時寫入同一張零列分頁時，會各寫一次標頭，第 2 列就會出現一列與標頭相同的重複標頭列。目前沒有任何防護；讀取端把那一列當格式不符的列計數、不採用，不遺失資料，但它會一直留在試算表裡、每次讀取都被算進格式不符。**本輪不處理，登記下一輪**（2026-09-26）。
- **分頁不存在**：讀取路徑視為「尚無資料」（⬜，不是錯誤）；寫入路徑建立分頁並寫一次標頭，再追加。比照 `repositories/pool_repository.py::_is_missing_worksheet` 的分流：只有「分頁真的不存在」才這樣處理，其他錯誤一律往上拋。
- **凍結第 1 列**（試算表畫面上捲動時標頭不動）與**保護第 1 列**（試算表的「保護範圍」，防止客戶在試算表裡手動改到標頭）：兩者都是試算表端的設定，不影響程式判讀。~~要不要做、由程式做還是客戶自己做，列入第 10 節。~~ → **保護第 1 列：客戶 2026-09-26 裁示（第 10 節 A2）**：由**客戶建檔時自己設定**，可編輯者為**客戶本人與服務帳戶**；程式**不**去設保護範圍（不需要額外的寫入權限與 API 呼叫）。保護範圍只是多一層防手滑，程式端照舊每次做 7.1 的標頭比對，不因有保護範圍而省略。⚠️ **凍結第 1 列不在這次裁示內**，維持未決，列在第 10 節 A2 列的備註。

## 9. 寫入頻率與 Sheets 配額估算

### 9.1 依據

- 本 repo 註解記載的配額：Google Sheets API 讀取「每使用者每分鐘 60 次」（`repositories/snapshot_repository.py` 在 `_QUOTA_BACKOFFS` 上方的註解；`services/nav_history_gs.py::append_points` 的 docstring 同樣寫 60 reads/min）。**寫入的配額，repo 內本組沒有找到記載**；以下暫以同為每分鐘 60 次估算。⚠️ 兩個數字本組都**沒有**對 Google 官方文件查證（本環境不連外）。
- **配額是算在服務帳戶頭上的**：五個 ui_v2 app（`49` §4.8，五個獨立行程）、舊 App、選股池、淨值累積、保單讀取，只要用的是同一個服務帳戶，就共用同一份每分鐘額度。本本的讀寫是**加在**既有用量上的，不是另外一份。

### 9.2 每個動作的次數（估算，未實測）

「打開」＝ `open_by_key` 一次讀取；讀多張分頁時用一次批次讀取（`values_batch_get`）同時拿標頭與資料。
