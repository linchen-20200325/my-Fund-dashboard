空狀態線框 —— 每次開 App 看到的第一個畫面

已核准的五頁線框是照「資料都載入好」畫的。這一份補上資料還沒進來時的畫面。 核心只有兩件事：哪些區塊該留占位、哪些該真的消失， 以及灰色（還沒載入）與紅色（真的出錯）怎麼分。 一樣只談結構與狀態，不談程式，需你拍板後才寫 UI 程式碼。

00 為什麼要補這一版

已核准線框的第 08 節自己寫了一句話：「動工前必須補查一次所有『資料不全時走另一套版面』的分岔， 漏一個就等於漏掉半個畫面。」補查做完了 —— 漏掉的比一半還多。

空狀態不是邊緣情況，是每次開 App 的第一個畫面

ui/helpers/session.py 的 INITIAL_SESSION_STATE 明確定義： macro_done=False、fund_data=None、portfolio_funds=[]。 這三個值由 app.py 在每次 session 啟動時注入 （init_session_state(st.session_state)）—— 也就是說每一次你打開這個 App，這三個值都是空的， 五頁全部從空狀態開始。

一句話

主版面是你按過按鈕之後才看得到的東西；空狀態是你每一次都會看到的東西。 現在的情況剛好相反：主版面畫了 2,100 行，空狀態畫了 0 行。

這份補版要回答的問題，只有三個

一該留還是該消失？資料不足時，每一張卡片是留一個灰色占位，還是真的整塊不見。 二灰的還是紅的？「還沒載入」和「真的壞了」現在長得一樣，所以你每次進站都看到一片紅。 三哪些畫面根本不必畫？盤點時找到一套 production 永遠到不了的版面，它應該被刪掉而不是被重畫。

01 現況：同一件事，這個專案有兩套相反的畫法

這不是「空狀態沒設計」，而是「空狀態設計過，但只做了一半」。 兩套慣例同時存在，而且就在同一個檔案裡。

證據：同一個函式，相隔 17 行，兩種相反的做法

ui/helpers/fund_grp_health/switch_section.py 的「🔀 換標決策建議」：

# ui/helpers/fund_grp_health/switch_section.py def render_switch_section(rows): _rows = [...] if not _rows: return ← 沒資料：整塊蒸發，畫面零痕跡 st.divider() st.markdown("### 🔀 換標決策建議") ← 標題寫在守衛「之後」 ... _reds = [...] if not _reds: st.info("目前無 🔴 紅燈（賣出／平轉）檔 —— 沒有急需換掉的標的。") return ← 有資料但結果為空：老實講出來

所以真正的問題不是「要不要設計空狀態」

而是守衛寫在標題前面還是後面。寫在前面 → 使用者看不到任何痕跡； 寫在後面 → 使用者看到標題和一句灰字說明。
這是一個位置問題，不是一個設計問題。 這一點決定了本次改動的規模比想像中小很多。

02 判準：哪些留占位、哪些真的該消失

不建議一刀切成「全部留占位」 —— 那會讓空畫面塞滿三十幾條灰字，比消失更難用。 下面是三個依序問的問題，前一個問完才問下一個。

判準依序問，命中即止
問一 這個區塊「該不該在這裡」，是固定的，還是取決於資料？
固定（它是頁面骨架的一部分，任何時候都該有一格）→ 往下問二。
取決於資料（例如「每一檔基金一個展開區」，0 檔就是 0 個）→ 消失是對的，不必占位。 問二 使用者為了看到它，已經做過那個動作了嗎？
已經按了按鈕／已經載入 → 絕對不能消失。他付出了等待卻沒得到解釋， 而且他無從分辨「這個功能不存在」和「這次沒算出來」。
還沒按 → 按鈕本身就是空狀態，不必再加一條灰字。 問三 它為什麼沒東西？
還沒給資料 → 灰色占位，而且必須寫出「去哪裡補」（照 signals.py 的寫法）。
結構上不適用（台幣計價基金本來就沒有匯率位階）→ 用既有的 ➖，或不顯示。

套用結果

按鈕還沒按的整頁下半部問二：還沒按不加占位。按鈕與輸入框就是空狀態
每檔一個展開區（逐檔深度分析、逐檔診斷）問一：取決於資料消失正確。0 檔就是 0 個展開區
台幣基金的匯率位階、無配息基金的配息欄問三：結構上不適用沿用既有 ➖，不要改成 ⬜（兩者語意不同，現況已分對）
整個功能對這個使用者不適用問三：不適用不顯示。不要留一個永遠灰著的占位

占位長什麼樣：三個要素，缺一不可

① 標題照印（使用者要知道這個功能存在）→ ② 一句話說缺什麼（不是「無資料」，而是「缺 1Y 含息報酬」）→ ③ 指出去哪裡補（「請先到 🌐 市場定調 按『📡 載入總經資料』」）。
第三點是最容易省掉、也最有價值的一點 —— 沒有它，占位只是把「消失」換成「灰色的消失」。

為什麼「業務紅燈」與「系統紅燈」一定要分開

這是本節最重要的一條，而且和 §1「錯誤的數字比沒有數字更危險」同源：
系統紅燈的意思是「這個數字不可信」；業務紅燈的意思是「這個數字可信，而且它很難看」。 兩者要你做的事完全相反 —— 前者要你別採信、去修；後者要你採信、去換基金。 用同一個紅色，等於把「不要相信這個畫面」和「相信這個畫面並據以行動」畫成同一件事。

市場定調頁：沒有 FRED 金鑰時，整個載入按鈕區塊不會被渲染 （if not FRED_KEY: 只印一行警告，兩顆按鈕在 else 裡）。 但同一頁的另一段照樣印「👆 點擊『載入總經資料』開始分析」—— 那顆按鈕在這條路徑上根本不存在。 tab1_macro.py ≈:824 / :1536-1537（兩個 if 是平行的，不是巢狀）

05 一套該刪掉、不該重畫的版面

盤點「個基深掘一頁有幾種版面」時，找到一套 production 永遠到不了的版面。 為看不到的畫面做設計是浪費，所以它列在這裡是建議刪除，不是待重畫。

個基深掘的五種版面（實測）

版面觸發條件規模使用者何時看到處置
空白fund_data is None（無 else）0 行每一次開 App要補（見第 04 節 ③）
失敗status == "failed"1 行抓取全敗維持
部分資料status == "partial"≈109 行常見（NAV 序列抓不到）維持，這一套寫得不錯

為什麼判定它到不了

# fund_fetcher.py :197 classify_fetch_status —— 只會回三個值 if has_name and has_series and has_metrics: # has_series = len(series) >= 10 return "complete" if has_any: return "partial" return "failed" # ui/tab2_single_fund.py if _status_fd == "failed": ... # :367 elif _status_fd == "partial": ... # :369 else: # :478 ← 只剩 "complete" 進得來 if s is None or s.empty or not m: # :483 ... ≈53 行的琥珀色卡片 # ← "complete" 保證 series≥10 且 metrics 非空 # 這個條件恆為 False

"complete" 的定義本身就要求序列至少 10 筆、且 metrics 非空； 而 else 分支只有 "complete" 進得來。 所以那個 if 在 production 路徑上恆為 False —— 那 53 行永遠不執行。

誠實說明這條判定的邊界

這是順著程式碼推出來的，不是實機跑出來的。它成立的前提是 status 一律由 classify_fetch_status 產生。 我查到的兩處寫入點（tab2_single_fund.py ≈:280、 services/moneydj_fetcher.py ≈:87）都寫成 x.get("status", classify_fetch_status(x)) —— 也就是若上游自己塞了第三種 status 字串，就會落進 else 而讓那段復活。
動工前要先確認沒有這種上游，確認後才刪。

06 需要你拍板的四件事

其餘（灰字寫法、要不要抽共用元件、改哪幾行、怎麼寫測試）都是技術細節，由團隊內部拍板。

Q1 判準用「三問」這一套，同意嗎？

重點是不一刀切：按鈕之後才跑的區塊一律留占位；按鈕之前不加占位； 數量取決於資料的（每檔一個展開區）維持消失。

我方建議 同意。理由：全部留占位會讓空畫面塞滿三十幾條灰字， 那只是把「消失」換成「灰色的消失」；而全部消失就是現在的問題。 分界點選在「使用者有沒有按過那顆按鈕」，是因為那正是他開始有預期的時刻 —— 按之前他不預期看到結果，按之後他預期。

Q2 顏色五態表（第 03 節），採用嗎？

關鍵是把業務紅燈（淘汰候選、吃本金）與系統紅燈（抓取失敗、渲染失敗）分開， 並把「未設定／未載入」統一成灰色。

我方建議 採用。決定性的理由：兩種紅色要你做的事完全相反 —— 系統紅要你別採信這個數字、去修；業務紅要你採信它、去換基金。 用同一個紅色，等於把「不要相信這個畫面」和「相信並據以行動」畫成同一件事。
附帶效益：那 39 處「用灰字印的真失敗」會一併被抓出來改回紅色。現在它們和「這格沒資料」長得一樣，等於失敗是隱形的。

Q3 · 我方追加 首頁最上方那條紅字「缺少必要金鑰」，要移走嗎？

它在 app.py 頂層無條件執行，因此五個分頁的最上方都會看到； 而且把可以降級使用的 GEMINI 稱為「必要」—— 同一支金鑰在其他四個地方分別被畫成橘色、藍色、灰色、以及完全不顯示。

我方建議 移到 ⑤ 設定與診斷的「🔑 API 金鑰狀態」一處，首頁只在缺 FRED 時留一行灰字。 判準：缺 FRED 會讓市場定調整頁不能用（擋路，值得提示）；缺 GEMINI 只是少了 AI 摘要（可降級，不該擋路）。
（若你希望開站就一眼看到金鑰狀態，替代方案是保留在側邊欄—— 側邊欄現在已經有一行 ✅／❌ 狀態列，而且用的是灰字，本來就是對的做法。但不建議維持現在「每頁最上方一條紅字」：它是你每次進站第一眼看到的東西，而它多半不代表任何故障。）

Q4 · 我方追加 那套永遠到不了的版面（≈53 行），刪掉還是留著？

個基深掘的「完整但序列為空」分支，在 production 路徑上條件恆為 False。 留著的成本是：下一個人重設計這一頁時會把它當成要維護的畫面， 而且它長得跟「部分資料視圖」很像，容易被誤認為是同一件事的兩份實作。

我方建議 先確認、後刪除 —— 動工前先查清楚沒有上游會塞第三種 status 值， 確認之後整段拔掉，並在交付報告列出刪除項目。 為看不到的畫面做設計，是這次補查最不該產生的成本。
（若你偏好保守，替代方案是暫時保留但改成一行「⬜ 非預期狀態」+ 記錄：這樣萬一它真的被走到，你會知道，而不是看到一張看起來正常的琥珀卡。代價是那段程式碼仍留在檔案裡。）
